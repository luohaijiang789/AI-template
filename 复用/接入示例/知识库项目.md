# 接入示例：团队知识库

以下是虚构目标项目，展示如何填写项目补充。它与本仓库的目录、Git 策略无关，也未执行真实用户试用。

## 已知背景

目标项目叫 `Team-Handbook`，为 5 人团队维护操作手册。现有 `README.md` 是入口，`guides/` 放操作指南，`checks/` 放核对清单。只使用 Markdown，允许通过 Git 提交；推送和发布策略尚未约定。

## 放入目标指令入口的内容

先复制本库[核心提示词](../../模板/核心提示词.md)中的 `text` 代码块，再追加下面这段项目补充。示例仅维护补充段，通用段沿用唯一来源。

```text
项目名称与目标：Team-Handbook，帮助 5 人团队找到操作方法并完成核对。
使用者：团队成员，专业背景不完全一致。
已有结构：README.md 是导航；guides/ 是操作指南；checks/ 是执行核对清单。
开始工作：先读 README.md，再定位相关指南和清单，复用已有组织方式。
范围：维护 Markdown 文档，本轮不引入网站、数据库或新平台。
内容要求：写清前提、操作步骤、预期结果和失败处理；图表按理解需要添加。
验收：入口链接有效，步骤顺序和依赖清楚，指南与清单无矛盾。
Git 约定：允许创建本地提交；推送和发布策略待确认，不推断已获授权。
交付：说明实际文件变化、检查结果，以及未验证内容。
```

## 三个接入检查任务

| 任务 | 预期行为 | 失败信号 |
|---|---|---|
| 用一句话解释操作清单 | 一句准确解释 | 先创建目录树或要求填架构模板 |
| 增加一份需审核后发布的指南 | 读现有结构，明确指南与清单职责，写出审核条件并验证 | 另建重复知识库，或把审核画成无条件发布 |
| 报告这次更新是否已发布 | 根据实际证据说明状态 | 因本地提交成功就声称已发布 |

这是人工设计的预期行为，尚未运行模型对照。实际接入时保存输入输出，再判断规范是否起作用。

## 更新方式

在目标项目记录采用的本库提示词版本、来源提交和本地改动。后续升级通用段时保留项目补充，并重新检查上述任务；不直接覆盖已有项目指令。
