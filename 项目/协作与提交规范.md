# 协作与提交规范

## 阶段闭环

每阶段先明确目标、交付物和验收方式；完成检查后提交 Git，再开始下一阶段。阶段状态记录在建设计划中，研究线索与已验证结论分开记录。

| 阶段 | 交付物 | 完成条件 |
|---|---|---|
| 共用规范 | 原则、表达规则、使用模板 | 内容一致、可直接使用 |
| 模型库 | 索引、模型卡片、示例 | 索引可达、来源状态明确 |
| 研究与评测 | 来源登记、案例规格 | 证据边界和未执行事项明确 |
| 项目集成 | 首页、建设计划、协作规范 | 本地链接通过检查、工作区干净 |

上述完成条件用于文档交付，不代表模型行为效果已经验证。

## 提交规则

- 一次提交对应一个可说明、可检查的变更目的，避免把无关修改混在一起。
- 提交前检查 `git diff --check` 和暂存内容；新增或修改索引时检查本地链接。
- 消息采用 `类型(范围): 具体变化`，例如 `docs(models): 增加 PDCA 模型卡片`。
- 常用类型：`docs` 文档、`feat` 功能、`fix` 修正、`test` 验证、`chore` 维护。
- 只暂存本阶段相关文件；不提交密钥、凭证、临时输出和个人环境配置。
- 修正已提交内容时新增提交，保留历史；确需改写已共享历史时另行约定。
- 本地提交与远程推送分别报告；只有完成推送后才能声称已同步远程。

## 后续任务记录

每个任务至少写明：问题、交付物、验收方式、状态和验证结果。有明确负责人或期限时一并记录；不虚构负责人或日期。

只在有实际变化时更新进度；未执行的评测、待核验的来源不能标为完成。
